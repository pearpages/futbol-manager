# Project audit, 3 October 2026, in plain words

This explains the two audits run on 3 October 2026 without assuming you know the code. Each
finding says **what is wrong**, **what a player or the owner would notice**, **how bad it is**
and **what the fix is**. The same findings are tracked as tick-boxes in [tasks.md](../tasks.md),
under _Audit 2026-10-03_ and _Architecture review 2026-10-03_. Tick them there; this file is the
explanation and does not change.

## What was audited

1. **The project audit.** Four reviewers checked four areas, and the serious findings were
   reproduced by hand:
   - **Game model**: are the rules of the game correct and fair?
   - **UI and accessibility**: does it look right on a phone, a tablet and a laptop, and can
     everyone use it?
   - **Code health**: is the code tidy and safe to change?
   - **Security and dependencies**: can anything bad get in, and are the third-party tools
     up to date?
2. **The architecture review**: is the code split into sensible parts that don't depend on
   each other more than they need to?

## The short version

- **Two bugs break the transfer market from the second season on.** Top foreign players become
  free, and you can strip a rival's squad until the game crashes. Fix these first.
- **On a phone, the game is hard to start and the main menu is cut off.**
- **The game's rules are checked in two places that disagree**: the screen and the engine.
  That is the root of several bugs, and the architecture review explains why it happens.
- **Nothing dangerous is exposed to the public.** There is no server and no personal data,
  and nothing shipped to players has a known vulnerability. The security points are about
  closing doors before someone needs them.
- **What already works well:**
  - Results are fully reproducible.
  - The money always adds up.
  - Every season has the right number of matches.
  - No secrets are in the code.

## Words you will meet

| Word                   | Meaning                                                                                                                                                        |
| ---------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Reducer** (`reduce`) | The game's engine. Every action (bid, change tactics, play a day) goes through it, and it decides what is allowed and what happens next.                       |
| **Command**            | One action sent to the reducer, such as "make a bid" or "advance a day".                                                                                       |
| **Store**              | The app's memory while you play: the current game plus which screen is open, the language, and so on.                                                          |
| **Domain**             | The package with the rules of football and money. No screens, no saving, just rules.                                                                           |
| **Seed**               | The number that the game's "randomness" starts from. Same seed plus same actions gives exactly the same career.                                                |
| **Harness**            | The automatic tests that simulate many whole seasons and check the results look like real football.                                                            |
| **Rollover**           | The jump from one season to the next: ageing, retirements, contracts ending, new youth players.                                                                |
| **Transfer window**    | The weeks when buying and selling are allowed.                                                                                                                 |
| **Contrast**           | How readable text is against its background. The accessibility standard (WCAG) asks for at least 4.5 : 1 for normal text.                                      |
| **Accessible name**    | What a screen reader says for a button or heading. "Renova" alone, repeated 25 times, is not helpful.                                                          |
| **Dependency**         | Third-party code the project uses, such as React or Vitest.                                                                                                    |
| **Dev dependency**     | A tool used only while building and testing. It never reaches players' browsers.                                                                               |
| **CSP**                | Content Security Policy: a rule in the page telling the browser which scripts and images it may load. A safety net against injected code.                      |
| **Coupling**           | How much one part of the code depends on the insides of another. Low is good: you can change one part without breaking the other.                              |
| **Cohesion**           | How much one file is about one thing. High is good: a file about transfers holds transfers and nothing else.                                                   |
| **Layer**              | One of the four packages, stacked: `domain` (rules) → `data` (clubs, players) → `persistence` (saving) → `app` (screens). Each may use only the ones below it. |

Severity: **High** means a player hits it or it breaks the game. **Medium** means it is wrong
and worth fixing soon. **Low** means tidy-up or a precaution.

## 1. Game model: are the rules right?

### High

**Foreign players become free after their contract runs out.**
Foreign clubs never give their players new contracts. Once a contract's end date passes, the
game values the player at zero, so any bid is accepted, even a fee of 1. By 2029 about half
the foreign players cost nothing. In a test, Málaga signed a player rated 92 for a fee of 1,
and the AI clubs also import most foreign players for free.
_Effect:_ from season two the market stops meaning anything, and so does the money.
_Fix:_ renew foreign contracts at each season change, the way Spanish clubs already do, and
add a test that no player anywhere holds an expired contract.

**You can strip a rival's squad until the game crashes.**
When you place several bids on the same AI club, each one is checked against the squad as if
the other bids weren't happening. All of them can be accepted. In a test, Santander was left
with 15 players and 2 forwards. Buying their defenders, the third signing crashed with an
error the game doesn't handle.
_Effect:_ an exploit that ruins a rival, and a crash.
_Fix:_ re-check the selling club's squad at the moment each deal completes, and refuse
politely if it would leave them unable to field a team.

**Stadium expansion is refused when you can afford it.**
The affordability check adds the 10% signing bonus used for transfers, but building work
doesn't pay that bonus. A club right at its overdraft limit is refused for a cost the screen
says it can pay.
_Fix:_ check the real building cost, and add a test right at the limit.

### Medium

- **You can change any club's line-up and tactics, not just your own.** The engine never checks
  whose team it is. A rival's ruined line-up stays all season, because AI clubs only rethink
  their line-up after a transfer or at the season change. _Fix:_ refuse commands for clubs you
  don't manage.
- **Any made-up formation is accepted.** "9-9-9" is accepted and later crashes the game. Some
  made-up shapes also beat every real formation for 7 of the 20 clubs. _Fix:_ accept only the
  listed formations.
- **AI offers can be accepted after the window shuts.** An offer made on 31 August can be
  accepted on 1 September, and the AI buyer can end up overdrawn. The game's own rules say
  neither should happen. _Fix:_ cancel offers when the window closes, and check the buyer can
  still pay.
- **The game keeps running after the season ends, and after you are sacked.** Pressing "advance a
  day" 140 more times after the last match pays four extra months of wages and opens a summer
  window. Starting the next season then moves the calendar backwards. Today only the buttons
  on screen prevent this. _Fix:_ the engine itself refuses.
- **Renewing contracts is the wrong move.** Renewing a player can lower their wage for free,
  and you can repeat it every summer. Letting a contract expire is cheaper than renewing,
  because the season change re-signs players below what a renewal would cost. _Fix:_ a
  renewal never goes below the current wage, and expiring players ask the same at the season
  change as they would in a renewal.
- **Sponsorship, crowds, the overdraft limit and the board ignore your actual squad.** They read
  a club rating fixed at the start of the career and never updated. Signing a star changes
  sponsorship by zero. _Fix:_ compute them from the current best eleven. This changes the
  game's balance, so the harness has to be re-checked.
- **Every new career starts from the same seed.** Two careers at the same club, played the
  same way, are identical. _Decision needed:_ give each career its own seed, or keep the fixed
  seed and write down why.

### Low

- Stadium expansion accepts half a seat (1000.5).
- A season can start with an empty list of names, so every youth player is called "Youth
  Player".
- Withdrawing a bid and bidding again on the same day gives two bids the same id.
- The market documentation says the free-agent pool stays at 20–31 players. It actually runs
  at 36–53.
- The player documentation says a formation's tempo is fixed, but made-up formations get
  around it.

### Checked and fine

- Same seed, same actions, same result, every time.
- The money adds up for every club, every season, over 12-season careers.
- 380 matches per season, 38 per club.
- No broken numbers anywhere in a long career, and no duplicate players.
- AI squads, when left alone, stay a sensible size and can always field a team.
- Contract offers, ticket prices and sales are checked properly.

## 2. UI and accessibility: can everyone use it, on any screen?

The automatic tests can't see layout, so this was checked in a real browser at phone
(390 px), tablet (768 px) and laptop (1280 px) widths.

### High

- **The main menu (the hub) is broken on phones and tablets.** At phone width the club name
  shows as "MADR", the league position and budget are cut off, the news button covers its
  heading, and tile labels spill out of their tiles. At tablet width the budget is still cut.
  _Fix:_ a one-column layout for narrow screens.
- **On a phone you can't see how to start a game.** On the club-picking screen the "Fes-te'n
  càrrec" button is pushed off to the right, with only a sliver showing, and tapping a club's
  row does nothing. _Fix:_ make the whole row tappable, or move the button.

### Medium

- **The settings menu doesn't close** with the Escape key or by clicking elsewhere.
- **Some text is too faint to read comfortably.**
  - The date and matchday in the title bar.
  - Red numbers for losses and debt.
  - White labels on the green Seguiment tiles.

  Each is below the 4.5 : 1 contrast standard.

- **The keyboard focus outline disappears on light panels**, because it is brass on beige. A
  keyboard user can't see which button is selected.
- **Buttons are too small to tap on a phone.** Column headers are 12 px tall, and the "i" buttons
  are 14 px. The guideline is at least 24 px.
- **The bottom bar takes 140 px of a phone screen**, wrapping onto three rows.

### Low

- Screen readers hear 25 identical "Renova" or "Ofereix" buttons with no player name, and
  table columns read as single letters ("J", "G", "E", "P").
- The hub's club heading is read as "Madrid MADRID".
- Headings with an "i" button inside them get "Explica: …" added to their spoken name.
- The language names in the settings menu are read in the wrong language's voice.
- The calendar's event rows use 10 px text.

### Old bugs explained

- **Found the cause of the known "page is 14 px too wide at 500 px" bug.** Hidden screen-reader
  text escapes its scroll box. A one-line CSS fix (`.screen { position: relative }`) was tested
  and solves it, on Squad too.
- **The known title-bar overflow is worse than recorded.** On a phone it pushes the settings cog,
  the only way to change language, off the screen.

### Checked and fine

- No sideways scrolling at tablet or laptop width.
- The page's language attribute follows the chosen language.
- No untranslated text in English.
- All images are correctly marked as decorative.
- No unnamed buttons.
- The keyboard order makes sense.
- The saves dialog traps focus and closes with Escape.
- Heading levels are correct, reduced-motion settings are respected, and zoom is allowed.

## 3. Code health: is the code tidy and safe to change?

Lint and type checks pass. The code follows the project's own rules well: no hidden
randomness, no hard-coded text, no inline styles, no type-safety escapes.

### Medium

- **The save-fixture tool writes a save the real game never writes.** `pnpm fixture` builds a
  game without the foreign league. The test for the next save-format upgrade would then check
  the wrong thing. Fix this before the next save-format change.
- **Two commands have no tests**: setting tactics and setting the ticket price. Their "out of
  range" refusals are never exercised.
- **The same calculation is written in two or three places.**
  - The seller's asking price.
  - The ticket price limits.
  - "Which club holds this player?"
  - A seed calculation that duplicates the standard helper.

  When one copy changes and the other doesn't, they disagree. That is exactly the stadium bug
  above.

### Low

- **Unused code.**
  - Three functions nobody calls.
  - One CSS class nobody uses.
  - Two dependencies declared in the wrong package.
- **Comments pointing at files that no longer exist.**
- **One rule (P11) says something stricter than the code does.** It says each package may only
  use the one directly below it, but the screens use the rules package directly 62 times.
  _Decision needed:_ reword the rule to "never import upwards", which is what the tooling
  actually enforces.

## 4. Security and dependencies: can anything bad get in?

**The big picture is reassuring.**

- The site is static: no server, no accounts, no network calls, no tracking.
- Saves never leave the player's browser.
- Nothing shipped to players has a known vulnerability.
- No secrets were ever committed.

### Medium

- **A damaged save locks the game until you clear your browser data.** If a save is corrupted or
  edited by hand, the game accepts it without checking. The page then goes blank, and because
  it reopens the last save on every visit, it stays blank. _Fix:_ check a save's shape before
  loading it, and show a "this save is damaged, delete it?" message instead of a blank page.
  This is essential before "import a save from a file" is added.
- **The "report a security problem" link doesn't work for outsiders.** security.md points to
  GitHub's private reporting, but that feature is switched off on the repository. _Fix:_ turn
  it on in the repository settings.
- **The development tools have 16 known vulnerabilities (5 high).** They are in the test runner
  (Vitest), the fake browser used in tests, and the linter. None of it reaches players, but it
  runs on the developer's machine and in CI. _Fix:_ a small Vitest patch update and a lockfile
  refresh.

### Low

- **No Content Security Policy.** The site could tell browsers to load only its own files,
  blocking injected scripts. The site is already simple enough for a strict policy.
- **The `main` branch is unprotected.** It can be force-pushed or deleted, and a push to `main`
  publishes the site. _Fix:_ a branch rule that blocks both and requires the checks to pass.
- **The CI file doesn't state its permissions.** It's safe today only because of a repository
  default.
- **Third-party CI actions are allowed and referenced by tag, not by exact version**, including
  one that runs in the publishing step. This is already a task; the audit added detail.
- **Dependabot alerts are off.** Free alerts would have flagged the vulnerabilities above in
  August.
- **The custom domain may not be verified with GitHub.** If the site were ever switched off while
  the DNS record stayed, someone else could claim the address.
- **`pnpm dev` is visible to everyone on the same Wi-Fi.** It should default to the developer's
  own machine.

## 5. Architecture: is the code split into sensible, independent parts?

### The good news: the layers hold

The four packages stack correctly: rules → data → saving → screens. Nothing reaches upwards,
and the tooling enforces it. The rules package is pure, every change to the game goes through
the engine, and the screens never poke at the store behind its back.

### The problem: two "everything" files, and screens that redo the rules

Imagine a restaurant where the waiters, not the kitchen, work out each dish's price from the
ingredients list. Sooner or later a waiter and the kitchen disagree. That is the main
architecture finding.

- **Screens recalculate the rules themselves.** The screens use 91 different pieces of the rules
  package, including the raw ingredients of prices and affordability. Each screen works out
  the answer on its own, which is how three of the audit's bugs arose. _Fix:_ the rules package
  offers ready-made answers, such as "what does this bid cost?" or "can I afford this
  expansion?". Screens and engine use the same answer.
- **The store does six jobs.** It holds the game, which screen is open, the language, the save
  slots, starting and ending careers, and "skip to next match". 22 files depend on it, and 14
  screens redraw on every tiny change. _Fix:_ split it into smaller stores, one per job.
- **The store also builds new careers.** It is the only place that knows the rules, the club data
  and saving all at once, and it keeps the shared random-number generator in a loose variable.
  _Fix:_ a separate "career" module that builds games; the store just holds the result.
- **The engine file is 1,520 lines.** It holds the list of every command and event, plus the
  handling for five different areas: line-ups, seasons, transfers, money and stadium, and the
  daily tick. The rules for transfers live in one file and their handling in another, so one
  change touches three files. _Fix:_ keep the engine as a switchboard, and move each area's
  handling next to its rules.
- **Club and name data is sent along with every "start new season" command**, so anything that
  starts a season must know the data package. _Fix:_ store that data once, when the career is
  created.
- **Market listings are built and shuffled inside the market screen**, where the season-simulation
  tests can't see them.
- **The rules package has no front door.** It lists about 236 things for anyone to use,
  including internal test helpers, in one flat folder of 22 files. _Fix:_ export only what
  other packages should use, and group files by area.
- **The screens folder is one flat folder of 37 files**, mixing screens, shared buttons and
  dialogs, feature panels and artwork. _Fix:_ folders per feature (market, squad, finances,
  league) plus shared UI and art.
- **Small knots.**
  - The league table is recalculated in 6 places on every redraw.
  - The translation system depends on the game store.
  - Three pairs of files import each other in a circle.

### What to do first

Because the architecture changes are a choice between real alternatives, the first step is
an **ADR**, a short written decision describing the target shape, agreed before any code
moves. After that the work can go in small steps that don't change how the game plays. The
check after each step is that a simulated season comes out byte-for-byte identical.

## Suggested order

1. **The two market bugs**: free foreign players, and stripping a rival's squad. They break
   every career from season two.
2. **The phone layout**: the hub and the club-picking screen.
3. **The engine's missing checks**: whose team, valid formations, offers after the window, the
   season end, the stadium check. Most are small and come with tests.
4. **Damaged-save protection**, before "import save" is built.
5. **Quick precautions**:
   - turn on private vulnerability reporting and Dependabot alerts;
   - update the dev tools;
   - protect `main`;
   - add CI permissions.
6. **Accessibility fixes**: contrast, focus, tap sizes, button names.
7. **The architecture ADR**, then the refactor in small, behaviour-neutral steps.
8. **Balance changes** (renewals, live club ratings) last, because they change how the game
   feels and need the harness re-run.

## Decisions only the owner can make

- Should each career get its own seed?
- Should rule P11 be reworded to match what the code and tooling actually do?
- What should the target architecture be (the ADR)?
